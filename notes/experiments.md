**다음 제출 전 우선순위**:
1. 연산자 희석 가설은 폐기/보류 -- 이번 "수정 확인"의 근거가 무효화됐으므로, 다음 회귀 시 로컬 인스턴스 하나로 성급히 원인 확정하지 않기.
2. 시간 비율 기반 로직(`STALL_TIME_FRAC`, 재시작 예산 등)을 다양한 timelimit(60s/300s/1200s 등)과 CPU 제한 조건(`taskset`/`cpulimit`로 4코어 흉내)에서 재검증해 서버 조건에 대한 민감도 확인.
3. 위 P4/P5/P6 가설(“Phase1/2가 예산을 다 먹는다”) 검증 -- 가장 크고 혼잡한 로컬 인스턴스를 긴 timelimit으로 돌려 Phase별 시간 소모 비율 측정.

## 2026-07-22 (이어서 2) -- 4차 제출 대비 40개 A/B 검증 중 prob_10 27배 회귀 발견 -> Phase 1 "deadline 절벽" 버그 진단/수정 -> 5차 제출 준비

**계기**: 위 항목 1(40개 재검증)을 실행하던 중, 4차 제출본(커밋 `692f3cb`) 대비 오늘 오전 변경분(#43~57) 전체를 60초 A/B 비교(`analysis/before_after_compare.py`)한 결과가 **23승 14패 3무**로 깨끗하지 않았음. `prob_10`이 196,955 -> 5,413,025(~27배)로 특히 심하게 악화됐고, 회귀 14개 전부 300블록 미만(MaxRects 무관)으로 확인.

**진단**: `prob_10`을 동일 코드·`seed=0`로 반복 실행하니 200,567/5,413,025/14,639,014로 자릿수 단위로 요동 -- 원인은 `_place_blocks`의 `phase1_deadline` 판정이 완전한 이진(binary) 스위치였다는 것. `time.time()`이 deadline을 넘는 순간부터 남은 블록 전부가 탐색 0회로 `_force_place`행. 몇 초의 순수 머신 타이밍 노이즈(같은 코드, 같은 seed인데 rank 140까지는 완전 동일한 배치였다가 그 이후 wall-clock이 8초 가까이 벌어짐)가 "블록의 20%를 탐색 0회로 날리느냐 마느냐"를 갈랐음. 기존 `hard_deadline`/`near_done_frac=0.05` 구제책은 "남은 5% 이하"일 때만 발동해서 이번 같은 20% 뭉텅이는 구제 못 함.

**수정**: `OVERTIME_SCAN_CAP=5`(최우선 bay 1개로 제한) 도입, `deadline`~`hard_deadline` 구간을 "저비용이지만 0은 아닌 탐색"으로 재정의(`near_done_frac` 기반 5% 게이트 완전 제거, 남은 블록 수 무관하게 전부 적용). 감사 결과 `_repair`(Phase 2)에도 같은 절벽이 있었음(자체 `timelimit*0.75` 강제배치 트리거가 새 `hard_deadline`보다 먼저 발동해서 무용지물이었던 것도 같이 발견/수정, 0.75->0.85로 정합). 상세 코드/근거는 `notes/algorithm_overview.md` #58 참고.

**검증**: prob_10 fix 후 3회 반복 -> 199,013으로 수렴(이전 200,567~14,639,014 요동, before=196,955와 동률 수준). prob_39(250블록, congested)로 `_repair` fix 확인 -> 312,642,282 -> 64,998,998 (~5배 개선). 회귀/개선/동률 섞은 11개 대표 인스턴스 재비교 -> 10승 1패(`prob_1`의 "패"는 8회 반복 재현 시도에서 재현 안 됨 -- restart 1이 8번 모두 68,633으로 결정론적이었고 최종값이 68,633보다 나빠진 적이 한 번도 없어 노이즈로 결론, 그 중 3회는 8,041로 수렴해 "prob_1의 진짜 최선"까지 재확인). **최종적으로 40개 전체를 20초라는 매우 짧은 예산으로 로버스트 테스트(`analysis/robustness_check.py`) -> 40/40 feasible, 크래시/infeasible/시간초과 0건.**

**남은 리스크(의도적으로 안 건드림)**: `_improve`(Phase 3)의 greedy 폴백(K≤12, xpress 실패시만)도 `hard_deadline` 없이 같은 절벽 가능성이 있으나, 이미 Phase 3 예산 끝자락이라 확장 시 오히려 전체 timelimit 초과(TLE) 위험이 있어 보류. `regret`/`batched` 우선순위 경로도 동일 결함 있으나 둘 다 폐기된 비활성 경로라 우선순위 낮음.
